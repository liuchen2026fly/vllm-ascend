# MegaMoe BF16 后续优化空间与调用方式校正（112 主机，2026-09-13）

**还有优化空间，但尚无新增生产优化或新增端到端收益。** 本次保持 V31 接入与 V30 内核不变，补测了生产实际使用的三维权重调用方式。四卡合成测试中，4096/6144/8192-token 完整局部链路仍分别慢于 CANN 原路径 22.33%/20.60%/17.93%。输入准备、主机发射以及设备计算都需要改善；不能仅依据旧二维权重脚本的开销作优化决策。

整网结论仍以 [112 主机四轮复现](megamoe_bf16_112_reproduction.md) 为准：4K 吞吐 -0.04%，6K -1.28%，未复现此前 18 主机的小幅收益。本次没有重跑整网，也没有改变这个结论。

## 1. 先纠正单算子与生产调用方式的差异

生产 `routed_experts.py` 在 local-partial 模式保留连续三维 BF16 ND 权重；`moe_comm_method.py` 的 `to_list` 将其封成单元素列表。因此传入 `[W1]`、`[W2]`，形状分别是 `[64,2048,1024]`、`[64,512,2048]`。

[原 V31 单算子复测](megamoe_bf16_v31_operator_report.md) 的 harness 却传入 `list(w1.unbind())`、`list(w2.unbind())`，每层 64 个二维 view。数值权重相同，运行时与内核版本也相同，但 TensorList 封装/元数据处理数量不同。原始测量保留为历史二维列表数据，不能当作完整对齐生产调用方式的测量。

本次 views/packed 两种方式分别执行 OFF A1 → ON B1 → ON B2 → OFF A2，并独立对照各自 OFF。二者所有输入和权重 SHA 相同。生产三维权重在 V26 已实现，本次是测量纠正，不能把相对旧 harness 的下降计为新代码收益。

## 3. 原生 profiling 显示的剩余开销

以下来自另一次 msprof，不与普通计时相减。先看不含输入准备和最终 AllReduce 的设备区间：OFF 从 routing 开始到 unpermute 结束；ON 为 MegaMoe task duration。四 rank 每次最大值及两个 block 中位数的均值：

| tokens | OFF 设备区间 μs | packed MegaMoe μs | 变化 |
| --- | ---: | ---: | ---: |
| 512 | 440.9 | 453.0 | +2.75% |
| 4096 | 839.1 | 927.3 | +10.52% |
| 6144 | 1082.2 | 1173.4 | +8.42% |
| 8192 | 1322.2 | 1444.9 | +9.28% |

再按每个样本 **ON 总区间最慢的 rank** 分解其准备、间隙和 MegaMoe。下面是 20 个选中样本的组件均值，不是上表的最大值中位数：

| tokens | packed 准备 μs | packed 准备后间隙 μs | packed MegaMoe μs | 旧 views 准备后间隙 μs |
| --- | ---: | ---: | ---: | ---: |
| 512 | 15.3 | 264.4 | 447.4 | 543.4 |
| 4096 | 57.8 | 231.6 | 908.4 | 519.5 |
| 6144 | 78.8 | 197.2 | 1168.5 | 485.2 |
| 8192 | 107.1 | 172.4 | 1441.6 | 477.0 |

8192-token 时，生产方式的准备+间隙约 279.6 μs，约占这一 profiling 区间的 16.2%。这只是所有该部分开销都消失时的区间时间上限，既不保证能全部消除，也不是端到端收益预测。内核本身相对 CANN 核心区间还慢约 122.7 μs（9.28%）。两项都值得优化。

旧 views 间隙 477.0 μs，packed 为 172.5 μs，而两组 8192 的 MegaMoe 组件均值分别约 1433.2/1441.6 μs。证据支持主要变化在准备后的主机调用/元数据通路；仅凭主 stream 空隙，不能把全部剩余时间归因于某个 Python 或 C++ 函数。

每 rank 的原生 API 统计均显示：244 次 `aclnnInnerMegaMoeGetWorkspaceSize`、244 次执行 API、仅 4 次 `aclnnInnerMegaMoeTiling`，对应四种形状。**不能声称每次都重新 tiling。** API 平均值含冷启动和异常长值，只用于调用次数审计，不与选定的热身后设备区间混算。

原 CSV 的绝对 μs 时间戳转为浮点后的最小间隔为 0.25 μs；组件加和的最大残差小于 0.25 μs。重算按时间戳精度检查，不把亚微秒舍入误差当成遗漏任务。

## 4. 优化优先级和精度约束

| 优先级 | 方向 | 证据与下一项有区分力的验证 |
| --- | --- | --- |
| 1 | 减少输入准备与发射开销 | 8K 有约 107 μs 准备和 172 μs 间隙；测试更合适的 Triton 拷贝分块、减少重复对象/描述符构造，先逐项测量再选实现。当前每次新分配保证连续调用独立，不能直接换成共享缓存。已有 tiling 缓存生效，不再重复未经证实的缓存补丁。 |
| 2 | BF16 GMM/激活流水和按形状选择 | 生产权重方式下 4K/6K/8K 设备仍慢约 8%–11%。当前 local-partial BF16 的激活按 62/2 专家两批通知，AIC 先完成 GMM1 再推进 GMM2。先采内部计算/搬运利用率及真实路由；确认等待占比后，才设计按 tile 工作量的流水。历史 V2/V4 只改激活分段已退化，不重复盲调。 |
| 3 | 小形状回退和真实模型路由复放 | 512 样本的完整局部链路慢 31.2%；当前 512 门槛需结合实际 token 分布重新评估。不能只抬门槛就宣称内核优化；必须验证目标整网的被选形状及端到端收益。 |
| 4 | 修正 CPU 绑核后独立做整网对照 | 112 实际 rank1/3 重叠；它影响的是主机部署条件，不能算作 MegaMoe 内核收益。OFF/ON 都采用同一修正计划，独立保存旧基线再验证。 |

本次没有改动生产算术。后续继续保留 BF16 舍入点、TopK 累加次序、local routed+shared 相加后再 TP 归约的顺序。最终 TP AllReduce 仍完成专家分片与 shared TP partial 的求和；当前完整复制输入分支没有可直接删除的实际输入 AllGather，local-partial 内核也已跳过跨卡 dispatch/combine。优化目标应针对实测的准备、计算和调度。

## 6. CPU 绑核问题已经定位，性能影响未验证

112 的 `npu-smi info -t topo` 和 PCI NUMA 都正确：NPU0/1 亲和 NUMA3（144–191），NPU2/3 亲和 NUMA2（96–143）。当前算法扩展到相邻 NUMA，再只拆分完全相同的 CPU 池；部分重叠池没有统一去重。使用真实输入执行原函数，复现以下结果，和四次服务日志一致：

| rank | 最终 CPU 池 | 主线程 | ACL / release |
| --- | --- | --- | --- |
| 0 | 0–47 | 2–45 | 46 / 47 |
| 1 | 144–191 | 146–189 | 190 / 191 |
| 2 | 96–143 | 98–141 | 142 / 143 |
| 3 | 144–191 | 146–189 | 190 / 191 |

同一算法在官方 [vLLM Ascend d4d2957](https://github.com/vllm-project/vllm-ascend/blob/d4d2957e5208c2f464d4625c05920bd29ea233cb/vllm_ascend/cpu_binding.py) 仍存在。最新合入的 #15517 设备映射修复没有改变这三个分池函数。离线 AST 复现与原函数一致，不依赖新的服务启动。OFF/ON 四次原服务使用相同分配，因此不能据此撤销已有负收益观测或声称它就是根因。
